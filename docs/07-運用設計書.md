## 1. 概要

本設計書では、ITSM Management / Service Desk のサービス運用に関する設計を定義する。

- サービス時間: 営業時間（9:00〜18:00）※Phase 3で24時間365日対応を計画
- 対象拠点: 本社 / 現場A / 現場B / 全拠点
- 利用者: 全社員（ITサービス利用者）＋IT運用部門（管理ユーザー）

## 2. サービスレベル（SLA）

### 2.1 優先度別対応期限

| 優先度 | 対応期限 | 対象例 |
|--------|----------|--------|
| critical（緊急） | 2時間以内 | 全社メール停止・基幹システム障害・セキュリティインシデント |
| high（高） | 4時間以内 | 複数ユーザー影響の障害・回線断 |
| medium（中） | 8時間以内 | 一部ユーザー影響・設定不具合 |
| low（低） | 24時間以内 | 単発の問い合わせ・依頼 |

> 設定画面（`system-settings`）で表示。実装時は `settings` APIで管理可能とする。

### 2.2 SLA計算ロジック

```
SLA遵守率 = (解決日時 ≤ SLA期限 のチケット数) / (解決済みチケット数) × 100

SLA状態（未解決）:
  - 期限超過 → urgent（超過）
  - 期限まで2時間以内 → risk（注意）
  - それ以外 → safe（安全）

SLA状態（解決済）:
  - 解決日時 ≤ 期限 → 遵守（成功）
  - 解決日時 > 期限 → 違反（緊急）
```

### 2.3 SLA監視

- **SLA監視画面**で期限超過・リスクチケットを常時一覧表示
- **ダッシュボード**で遵守率・違反数をKPI表示
- Phase 3で「SLA期限30分前のTeams通知」等の自動通知を実装（Automation連携）

## 3. 運用フロー

### 3.1 インシデント運用フロー

```
ユーザー（利用者）              ヘルプデスク（operator）
       │                              │
       │  障害・問い合わせ発生          │
       ├──────────────────────────────▶│  1. インシデント起票
       │                              │     (優先度・カテゴリ・対象システム)
       │                              │  2. 一次対応・状況確認
       │                              │  3. 担当者割当（必要時）
       │                              │  4. 対応・解決
       │◀──────────────────────────────│  5. 解決報告（ステータス: resolved）
       │                              │  6. クローズ（ステータス: closed）
       │                              │
       │         フィードバック         │
```

### 3.2 問題管理フロー（RCA）

```
インシデント複数発生
    │
    ▼
問題として起票（調査中）
    │
    ▼
根本原因分析（RCA）
    │
    ├─▶ 既知エラー登録（known_error / KEDB）
    │        └─▶ 回避策（workaround）をナレッジ化
    └─▶ 解決（resolved）→ 変更管理へ連携（恒久対策）
```

### 3.3 変更管理フロー（CAB）

```
変更申請（draft）
    │
    ▼
レビュー（review）
    │
    ▼
CAB承認（approved）
    │
    ▼
実施（implementing）
    │
    ├─▶ 成功 → クローズ（closed）
    └─▶ 失敗 → ロールバック → 却下（rejected）
```

### 3.4 サービス要求フロー

```
申請（pending）
    │
    ▼
承認待ち（approving）
    │
    ▼
対応中（in_progress）
    │
    ▼
完了（completed）／却下（rejected）／取消（cancelled）
```

### 6.4 ロールバック手順

Cloudflare Workers はデプロイメント単位で即時ロールバック可能。

```bash
npx wrangler deployments list       # 対象バージョンIDを確認
npx wrangler rollback               # 直前のデプロイメントへ戻す
# 特定バージョンへ戻す場合
npx wrangler rollback --message "rollback to <version-id>"
```

**ロールバック判断基準**:
- ヘルスチェック失敗（`GET /api/health` が 200 以外、DB 接続エラー）
- 主要画面（ログイン → ダッシュボード）が操作不能
- API の 5xx エラー率が急上昇（Workers ログ・NEL で監視）

**DB ロールバック**: スキーマ変更は追加マイグレーションのみの原則のため、コードロールバックだけで原則対応可能。データ不整合が疑われる場合は Cloudflare D1 のバックアップ機能で過去状態を確認する（要 admin 判断）。

### 6.5 監視

| 対象 | 方法 |
|------|------|
| アプリケーション | `GET /api/health`（DB 接続・レイテンシを返却）。Workers ログ（Cloudflare Dashboard > Workers > Logs） |
| エラー率 | Workers の `[observability] enabled = true` 設定（トレース・ログ永続化） |
| 異常時対応 | ロールバック手順（6.4）に従う。追加変更を重ねず、安全なロールバックを優先 |
| DB | Cloudflare Dashboard > D1（サイズ・クエリ）。`wrangler d1` で管理 |

> **注意（Deep Debug 2026-09-13 の実測）**: 本番カスタムドメインは Cloudflare Access 配下にあるため、
> 未認証の `GET /api/health` は **302（Access ログインへリダイレクト）** を返す。
> 外部監視で 200 を判定するには、Access に `/api/health` の Bypass ポリシーを追加するか、
> 監視対象を `https://<worker>.workers.dev/api/health` へ変更すること。
> 現状のままでは 6.4 のロールバック判断基準（「`/api/health` が 200 以外」）が常時成立してしまう。

### 6.6 D1（SQLite）実装上の制約 — 環境差に注意

**`SQLITE_MAX_COMPOUND_SELECT` が本番 D1 では 5**（2026-09-13 実測）。

| 環境 | 上限 | 6 項の UNION ALL |
|------|------|------------------|
| Cloudflare D1（本番） | **5** | `too many terms in compound SELECT: SQLITE_ERROR` |
| node:sqlite（ローカル / CI） | 500 | 成功 |

つまり **「ローカルと CI では通るが本番だけ 500 になる」** という環境差が生じる。
複数テーブルの集計を `UNION ALL` で 1 文にまとめてはならない。

- 集計は `D1Client.queryMany()`（D1 の batch に SELECT を並べる）を使う。
  実行回数は 1 リクエストのままで、項数制限も受けない
- 実例: `GET /api/dashboard/summary` は 8 テーブルの件数を `UNION ALL` で
  まとめていたため本番のみ 500 になった（本改修で `queryMany()` へ変更）

> **教訓**: SQLite の挙動差はローカルテストで検出できない。
> 集計系の SQL を変更したら、**デプロイ後に本番エンドポイントの 200 を確認**すること。

## 7. 運用体制

| ロール | 担当 | 責任 |
|--------|------|------|
| サービスデスク（1次） | ヘルプデスク | 受付・一次対応・解決 |

| システム管理者 | admin | ユーザー管理・設定・監査 |
| 運用監視 | インフラ課 | リアルタイム監視・障害検知 |

## 8. トラブルシューティング

| 症状 | 原因 | 対応 |
|------|------|------|
| ログインできない | パスワード誤り / アカウント無効 | パスワードリセット・is_active確認 |
| APIが401 | トークン失効 | 再ログイン（Phase 1: リフレッシュ） |
| 403 | ロール不足 | adminに権限変更依頼 |
| 一覧が表示されない | API障害・DB接続 | `/api/health` 確認→DB疎通確認 |
| SLA超過が多数 | 人員不足・対応漏れ | SLA監視画面で優先対応・工数調整 |
| 監査ログ欠落 | コード修正 | 全CRUDに監査実装されているか確認 |

## 9. 運用時の留意事項

1. **データの機密性**: セキュリティイベント・監査ログは管理者のみ参照
2. **既知エラーDBの維持**: 解決済み問題はナレッジ記事として公開し、再発時の対応時間を短縮
3. **SLAリスクの早期検知**: ダッシュボード・SLA監視画面を毎朝確認
4. **変更の事前連絡**: 緊急変更以外は事前にCAB承認を取得
5. **パッチ適用の計画**: 対象台数・適用率をパッチ管理画面で追跡
