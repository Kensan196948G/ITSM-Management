## 1. 全体アーキテクチャ

### 1.1 アーキテクチャ概要

本システムは **SPA（Single Page Application）＋ REST API** の2層構成を採用する。

```
┌─────────────────────────────────────────────────────────┐
│                     クライアント (Web)                    │
│  React 18 (SPA)  ── 現行: CDN + Babel 単一HTML            │
│  ── Phase 2: Vite + TypeScript へ刷新                     │
└──────────────┬──────────────────────────────────────────┘
               │ HTTPS / REST (JSON)
               ▼
┌─────────────────────────────────────────────────────────┐
│               バックエンド (Python FastAPI)                │
│  Router 層 → Service 層 → Model 層 (SQLAlchemy ORM)       │
│  認証: JWT / OAuth2Password / bcrypt                     │
│  認可: RBAC (viewer < operator < manager < admin)        │
│  監査: AuditLog (操作前後JSON)                            │
└──────────────┬──────────────────────────────────────────┘
               │ SQLAlchemy
               ▼
┌─────────────────────────────────────────────────────────┐
│                     データベース                           │
│  現行: SQLite (開発) / Phase 3: PostgreSQL                │
└─────────────────────────────────────────────────────────┘
```

### 1.2 技術スタック

| 層 | 技術 | 現行 | Phase 2以降 |
|----|------|------|-------------|
| フロント | フレームワーク | React 18.3.1（UMD CDN） | React 18 + TypeScript |
| | ビルド | Babel standalone（ブラウザ内変換） | Vite |
| | スタイリング | CSS変数 + oklchカラー / v2トークン | デザイントークン体系 |
| | 状態管理 | React Hooks（useState/useMemo等） | TanStack Query |
| | API連携 | MockAPI（ブラウザ内モック） | OpenAPI → TS型自動生成 |
| バックエンド | フレームワーク | FastAPI | 同左 |
| | ORM | SQLAlchemy 2.0 (Mapped/mapped_column) | 同左 |
| | DB | SQLite（開発） | PostgreSQL |
| | 認証 | python-jose (JWT) + bcrypt + OAuth2PasswordBearer | 同左 + Refresh Token |
| | キャッシュ | — | Redis（Phase 3） |

## 2. フロントエンド設計

### 2.1 画面構成（現行 `index.html`）

単一HTMLに全画面を内包する。ReactコンポーネントはBabelでブラウザ内変換される。

```
index.html
├── CSS設計トークン (oklch ベース、ライト/ダークテーマ)
├── モックデータ層 (MockAPI / window.ITSM_USERS / window.__ITSM_DATA)
├── ICONS (lucide風インラインSVG 27種)
├── TONES / LABELS (ステータス・優先度の色と日本語ラベル)
├── UIプリミティブ
│   ├── Btn / KPI / Empty / SearchInput / FilterSelect
│   ├── Modal / ConfirmDialog
│   ├── DataTable / Pagination
│   └── チャート: BarChart / LineChart / DonutChart (SVG)
├── レイアウト
│   ├── Sidebar (折りたたみ・セクション・メニュー検索)
│   └── Header (テーマ切替・通知・タイトル)
├── ビュー
│   ├── DashboardView
│   ├── ModuleView (汎用CRUDビュー + MODULE_CONFIGS)
│   ├── SLAView / RealtimeView / VisualizationView / AutomationView
│   └── SettingsView
└── App (ルーティングはactiveViewステートで切替)
```

### 2.2 ルーティング方式

- URLルーティングライブラリは使用せず、`activeView` ステートによる画面切替を採用
- 表示中画面は `localStorage('itsm-view')` に永続化（リロード後に復元）
- 画面遷移時は `itsm-main` をスクロールトップへ戻す

### 2.3 状態永続化（localStorage）

| キー | 値 | 内容 |
|------|-----|------|
| `itsm-dark` | `"true"` / `"false"` | ダークモード |
| `itsm-collapsed` | `"true"` / `"false"` | サイドバー折りたたみ |
| `itsm-view` | モジュールキー | 表示中画面 |

### 2.4 汎用モジュールビュー（ModuleView）

`MODULE_CONFIGS` にモジュール定義を宣言し、共通の一覧・検索・フィルタ・CRUD・詳細表示を提供する。

```
MODULE_CONFIGS[moduleKey] = {
  key, label, sub, dataKey, ticketField,
  kpis: (data) => [...],           // モジュール固有KPI
  columns: [...],                   // テーブルカラム定義
  filters: [...],                   // フィルタ定義
  formFields: [...],                // フォーム定義
  defaults: {...},                  // 新規作成時の初期値
}
```

### 2.5 ステータス・優先度のトーン定義

| 値 | 日本語ラベル | トーン |
|-----|--------------|--------|
| critical / high / medium / low | 緊急 / 高 / 中 / 低 | danger / warning / info / success |
| open / in_progress / waiting / resolved / closed | 新規 / 対応中 / 保留 / 解決済 / クローズ | info / warning / info / success / neutral |
| active / maintenance | 稼働中 / 保守中 | success / warning |
| draft / review / approved / implementing / rejected | 下書き / レビュー中 / 承認済 / 実施中 / 却下 | neutral / info / success / warning / danger |
| investigating / known_error | 調査中 / 既知エラー | warning / danger |
| detected / contained | 検知 / 封じ込め | danger / warning |
| pending / approving / in_use / stock | 未処理 / 承認待ち / 使用中 / 在庫 | info / info / success / neutral |
| planned / testing / deploying / completed / failed / cancelled | 計画中 / テスト中 / 展開中 / 完了 / 失敗 / 取消 | info / info / warning / success / danger / neutral |
| published / archived | 公開済 / アーカイブ | success / neutral |
| operational / degraded / incident | 正常 / 低下 / 障害 | success / warning / danger |
| admin / operator / manager / viewer | 管理者 / オペレータ / マネージャ / 閲覧者 | danger / info / warning / neutral |

### 2.6 チャート設計

すべてSVGで実装し、データを塗りつぶしで表現する（空のアウトラインのみを禁止）。

| チャート | 用途 | 特徴 |
|----------|------|------|
| BarChart | 優先度別分布 | グリッド線・値ラベル付き |
| LineChart | 7日トレンド | エリア塗り + データポイント + 値ラベル |
| DonutChart | SLA遵守率 | 中央ラベル + 凡例 |

### 2.7 リアルタイム監視の設計

- 5秒間隔の `setInterval` で `tick` を更新し再描画
- システム状態は静的配列（デモ）。Phase 3で監視API連携
- 状態別のドット色: operational=success / degraded=warning / incident=danger

## 3. バックエンド設計

### 3.1 3層アーキテクチャ

```
app/
├── main.py            — FastAPI エントリ、CORS、ルーター登録
├── core/
│   ├── config.py      — 設定（app_name, version, secret_key, debug 等）
│   └── security.py    — bcrypt/JWT/RBAC ユーティリティ
├── db/
│   ├── base.py        — SQLAlchemy Base
│   └── session.py     — エンジン・セッション・get_db
├── models/            — ORMモデル（User, Incident, IncidentComment, AuditLog 等）
├── schemas/           — Pydanticスキーマ（Request/Response）
├── routers/           — エンドポイント定義（API層）
├── services/          — ビジネスロジック（サービス層）
└── utils/
    ├── sla.py         — SLAステータス計算 (safe/risk/urgent)
    └── ticket_no.py   — チケット番号採番 (INC-YYYY-XXXX)
```

### 3.2 認証設計

- **パスワード**: bcrypt（`bcrypt.hashpw` + `gensalt`）でハッシュ化保存。平文保存なし
- **トークン**: JWT（python-jose）。`exp`（有効期限）と `sub`（ユーザーID）を含む
- **取得方式**: OAuth2PasswordBearer（`tokenUrl="/api/auth/login"`）
- **依存注入**: `get_current_user` でトークン検証 → ユーザー取得（非アクティブは401）
- **トークン有効期限**: `settings.access_token_expire_minutes`（デフォルト分）

### 3.3 RBAC 設計

```python
role_order = ["viewer", "operator", "manager", "admin"]

def require_role(minimum_role: str):
    # 現在ユーザーのロール順位 < 要求ロール順位 → 403 Forbidden
```

| エンドポイント | 要求ロール |
|----------------|------------|
| 参照系（GET /list /detail） | 全ロール（認証必須） |
| 作成・更新・削除 | operator 以上 |
| ユーザー管理・システム設定 | admin（設計） |

### 3.4 監査ログ設計

`AuditLog` モデルに重要操作（create / update / delete）を記録する。

| フィールド | 内容 |
|------------|------|
| `entity_type` | 対象エンティティ（例: `incident`） |
| `entity_id` | 対象レコードID |
| `action` | create / update / delete |
| `before_json` | 更新前のスナップショット（JSON文字列） |
| `after_json` | 更新後・作成後のスナップショット（JSON文字列） |
| `user_id` | 操作ユーザー |
| `ip_address` | 操作元IP |

スナップショットは `json.dumps({column: str(value)})` 形式で全カラムを文字列化して保存する。

## 7. 開発・実装時の注意事項

### 7.1 設計原則

1. **変更は要件定義・仕様書と同期させる**（`docs/` がソース・オブ・トゥルース）
2. 既存 `index.html` の機能を**削減せず**、刷新時に機能同等性を保つ
3. モックデータ層（MockAPI）はAPI連携時にインターフェース互換で置換する
4. 新規コンポーネントは `v2/` の設計トークン（`--c-primary-*` 等）を基準にする

### 7.2 既知の技術的制約

| 制約 | 対応方針 |
|------|----------|
| React CDN + Babelは本番不向き（セキュリティ・性能） | Phase 2でVite + TypeScriptへ移行 |
| 単一HTMLの肥大化（約1,900行） | コンポーネント分割・コード分割 |
| モックデータがJS内に直埋め | API実装後にMockAPIをAPIクライアントへ置換 |
| ルーター未使用（activeView切替） | Phase 2で React Router 導入を検討 |

### 7.3 実装開始時のチェックリスト

- [ ] Phase 1 セキュリティ対応（CSP/HSTS/CORS/Rate Limit/Refresh Token）
- [ ] APIスキーマの確定（OpenAPI生成）
- [ ] データモデル全エンティティの実装（incidents以外の8モジュール）
- [ ] フロントのAPI連携（MockAPI → 実API置換）
- [ ] 認証フロー（ログイン画面・トークン管理）の実装
- [ ] テスト基盤（pytest / Vitest / Playwright）構築
