## 1. はじめに

### 1.1 目的

本システムは、ITサービスマネジメント（ITSM）を実践するための統合管理基盤である。ITILの実践領域（インシデント管理・問題管理・変更管理・構成管理・ナレッジ管理・資産管理・パッチ管理・セキュリティ管理・サービス要求管理）を、**Service Desk** を中心とした1つのWebコンソールで一元的に管理することを目的とする。

### 1.2 背景

現状、IT運用部門では障害対応・変更作業・資産管理・ナレッジ共有が各ツールやExcel・口頭連絡で分散管理されており、以下の課題がある。

- 障害の「起票→対応→解決」の履歴が残らず、再発時の引き継ぎが困難
- SLA遵守状況が可視化されておらず、期限超過に気づくのが遅れる
- 変更管理・資産管理・パッチ管理が属人化し、監査対応に時間がかかる
- 各拠点（本社・現場A・現場B）の状況を一覧で把握できない

### 1.3 システム化の範囲

- **対象範囲**: ITサービスデスク業務全般（障害・問い合わせ・変更・資産・セキュリティ等の受付・管理・分析）
- **対象ユーザー**: IT管理課・ヘルプデスク・インフラ課・総務部
- **利用形態**: 社内イントラネット上のWebアプリケーション（デスクトップWeb前提、レスポンシブ対応）

## 2. 用語定義

| 用語 | 定義 |
|------|------|
| ITSM | ITサービスマネジメント。ITサービスの設計・提供・運用・改善を統合管理するフレームワーク |
| ITIL | ITSMのベストプラクティス集。本システムはITIL 4の実践領域を参考に設計 |
| Service Desk | ユーザーからの問い合わせ・障害連絡の単一窓口。インシデント・サービス要求の受付を担う |
| インシデント | サービスの中断または品質低下を引き起こす事象（障害・問い合わせ） |
| 問題（Problem） | 複数インシデントの根本原因。RCA（根本原因分析）と既知エラー管理の対象 |
| 変更（Change） | 本番環境への変更作業。CAB（変更諮問委員会）承認を経て実施 |
| CMDB | 構成管理データベース。IT構成要素（CI）とその関係を管理 |
| CI | 構成アイテム。管理対象となるサーバ・ネットワーク機器・サービス等 |
| KEDB | 既知エラーデータベース。既知の障害と回避策を蓄積 |
| SLA | サービスレベル合意。対応期限・遵守率などのサービス品質基準 |

## 3. ユーザーとロール

### 3.1 ロール定義（RBAC）

システムは以下の4ロールでアクセス制御を行う。

| ロール | 概要 | 主要権限 |
|--------|------|----------|
| `viewer`（閲覧者） | 参照専用ユーザー | 全画面の閲覧 |
| `operator`（オペレータ） | 実務担当者（ヘルプデスク・インフラ課） | 閲覧＋インシデント/問題/変更等の登録・更新・削除 |
| `manager`（マネージャ） | 部門管理者 | operator権限＋承認・設定変更 |
| `admin`（管理者） | システム管理者 | 全権限＋ユーザー・ロール管理、システム設定 |

**ロール階層**: `viewer` < `operator` < `manager` < `admin`

> 実装根拠: `backend/app/core/security.py` の `require_role` および `role_order` 配列。

## 7. 現状評価と課題（既存実装の精査結果）

`ITSM-WebUI-Evaluation.html` の評価（総合 **54/100**）と実装精査から、以下を既知の課題として定義する。

| 領域 | スコア | 課題 |
|------|--------|------|
| 機能カバレッジ | 85 | ITIL準拠の14管理領域を網羅。機能面は良好 |
| API設計 | 75 | 3層アーキテクチャ・監査ログ組込みは堅実。レスポンス統一が今後必要 |
| バックエンド品質 | 70 | 実装は良好。N+1クエリ解消等が課題 |
| テスト充実度 | 60 | テスト不足。カバレッジ向上が必要 |
| UI/UX品質 | 40 | 単一HTMLの肥大化。コンポーネント分割が急務 |
| フロント設計 | 30 | React CDN + Babel構成からVite + TypeScriptへ刷新が必要 |
| アクセシビリティ | 20 | aria-label等の最低限対応が急務 |
| セキュリティ | 50 | CSP/HSTS・Rate Limiting・Refresh Token未導入 |

**開発フェーズ方針**（詳細は `09-開発計画書.md` 参照）:

1. **Phase 1（〜1ヶ月）**: セキュリティ緊急対応（CSP/HSTS・CORS厳格化・Rate Limiting・Refresh Token）
2. **Phase 2（2〜3ヶ月）**: フロント基盤刷新（React+TS+Vite・コンポーネント化・API統合・テスト80%）
3. **Phase 3（4〜6ヶ月）**: プロダクション品質（PostgreSQL・Redis・E2E・MFA・CI/CD）
